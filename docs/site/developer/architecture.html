Architecture

How a keystroke in a terminal becomes somebody walking across a room, and where the seams are.

The pipeline

your harness              a hook fires with a JSON payload on stdin
   │                       ...or, for OpenClaw, an in-process hook bus
   ▼
bin/aop-send.cjs          one adapter for every hook-based harness:
   │  + mappers/*.cjs     payload -> AOP events, tool names -> tool_class,
   │                      redaction applied here, before anything leaves
   │
   │  openclaw-plugin/    the same job for a harness that never spawns a process:
   │                      a long-lived plugin, so it batches and can heartbeat
   │                      (both routes share bin/lib/aop-core.cjs)
   ▼
server.cjs                the receiver: token-checked ingest, ring buffer,
   │                      SSE fan-out, replay of sessions still in flight
   ▼  SSE
src/data/aop-reducer.js   the one reducer: AOP -> stage directions
   │                      ("this person arrived", "they are researching X",
   │                       "they are on part 2 of 5")
   ▼
src/data/feeds.js         one feed per source the office selected, merged into
   │                      one stream: ids namespaced, states summarised
   ▼
src/agents/AgentManager.js  stage directions -> behaviour: who has which desk,
   │                        who walks where, whose post is in the box
   ▼
src/agents/states.js      an action queue per character, ticked every frame
   │
   ▼
scene/* and ui/*          meshes, and the panels that describe them

These rules hold that chain together.

Redaction happens at the near end. The adapter decides what leaves your machine, not the office and not the server, so a decision about privacy is made once, in the process that already has the secret. See Sources.

There is exactly one reducer. server.cjs holds a ring buffer and nothing else — it does not interpret events, and it does not know what a desk is. All translation from AOP into office behaviour is in src/data/aop-reducer.js — extracted from AopSource, which keeps the transport, precisely so the rules can be tested against recorded streams with fake clocks (test/aop-reducer.test.js) — so there is one place to look when the room disagrees with reality.

Every source is the same shape. src/data/AgentSource.js is the interface; MockSource and AopSource both implement it, sources.js declares the six sources and how each is built, and nothing downstream can tell them apart. Optional capabilities are feature-detected rather than branched on by name — that is why T vanishes when nothing selected can invent a job, without the UI knowing what a mock is.

An office is a set of sources, and feeds.js is where that stops mattering. It starts one feed per selected source, prefixes every id with the feed it came from so two harnesses cannot collide on a session id, and collapses their separate connection states into the one line a pill can hold. Downstream of it there is a single stream of stage directions again, so nothing in the room has to reason about how many harnesses it is looking at — only an agent's own mark and detail panel ever name one.

The set moves without the room moving. feeds.sync() takes a new choice of sources and shifts only the difference: feeds still chosen are left running untouched, feeds that went are stopped and dropped, and feeds that arrived are built and started on the spot. Removing a source is not the same as removing its people, so it hands the removed definitions back and AgentManager.showOut() walks those characters out of the building on the ordinary path — desk given back, coat off the stand, lift, door. The office used to answer this by rebuilding the world, which took the building, the furniture and every other feed's agents with it.

Observation beats the feed where the room can see for itself. The mid-job coffee run is timed by AgentManager counting seated working time, not sent by any harness, so it works for every source including ones that could never report it.

Appearance changes preserve the running office. world.changeAppearance() replaces the shell, outlook and lights while retaining the world root, furniture handles, AgentManager, feeds and UI subscriptions. Palette-key materials repaint the retained props; sill planting is rebuilt for the season. Disposal excludes resources still used by the retained root. Interior actions and reservations stay intact, walks replan, and an agent using a replaced entrance transfers to the new landing with queued work kept. An unchanged lift inherits its state. Mail and courier queues continue to deliver once. Switching to a different scene still uses full teardown and starts that scene's feeds.

Receiving events

server.cjs is both the static dev server and the AOP receiver:

Endpoint Who calls it
POST /office/<keycard>/aop/v0/events Harness adapters, with the URL and token from ~/.roving-office/endpoint.json
GET /office/<keycard>/aop/v0/stream The browser, over SSE — one harness at a time with ?harness=, or all of them without it (the debug log); ?after=<cursor> replays from the buffer
GET /office/<keycard>/aop/v0/state The browser on load, to replay sessions still in flight
GET /office/<keycard>/aop/v0/health You, wondering whether anything is connected
GET/POST /office/<keycard>/aop/v0/tokens, DELETE .../tokens/<id> You, adding a second machine to an office or taking one away — each needs a token you already hold
DELETE /office/<keycard>/api The keycard dialog, closing the office — needs its write token
POST /office/<keycard>/api/passcode The same dialog setting or clearing a passcode (write token), or a visitor typing one (nothing)

Every office has its own 2 000-event ring buffer and nothing else, and the surface is gated per route rather than per network: a keycard is enough to watch an office from another device, and not enough to inject agents into one. Reads (/stream, /state, /health) need only the keycard already in the URL; POST /events needs a token as well — either the local receiver's own per-process one from endpoint.json, or one of the office's own write tokens. That second kind is what lets a laptop feed an office running on a server somewhere rather than on the machine the agents are on. An office holds a list of them, so a second machine can be added and one machine taken away without disturbing the others: POST /api/offices returns the first, and GET/POST/DELETE on /office/<keycard>/aop/v0/tokens list, mint and revoke the rest — each requiring a token, never the keycard alone (aop-spec.md §5.5.1). All reduction from AOP into office behaviour happens in src/data/aop-reducer.js, so there is exactly one reducer in the system.

Owning an office, and the optional passcode

Holding an office's write token is the whole of owning it. There is no account, no sign-up and no user store, and there is not going to be one. POST /api/offices returns the office's first token exactly once, and the browser that asked keeps it in localStorage (src/office/owner.js); the CLI keeps its copy in endpoint.json. Every privileged act asks for that token and nothing else, which is the same rule the token routes above already followed — capability begets capability. For a long time the browser read the keycard out of that response and dropped the token on the floor, so an office cut at reception was permanently unownable: nothing could add a machine to it, revoke a token on it or close it when its link leaked.

Two acts hang off it, both refused outright on the reserved demo office — asked of the keycard rather than of office.reserved, so the answer does not change depending on whether anything has instantiated that room yet:

  • DELETE /office/<keycard>/api closes the office, over store.remove(), which already closed the bus and hung up every watcher for the reaper's sake. It revokes everything at once, and it has one property worth knowing: because visiting an unknown keycard creates an office, a closed office cannot 404. The leaked link opens an empty room and whoever kept it is told nothing.
  • POST /office/<keycard>/api/passcode sets, changes or clears an optional read passcode — scryptSync with a per-office salt, because a passcode is a handful of characters a person chose and the store file sits on a mounted volume. The same route with no token is an unlock attempt.

A successful unlock is answered with a cookie, and one rule holds the arrangement up: a seal may only ever admit a read; a write always needs a header token. Every read it covers is an idempotent GET, so there is no CSRF to have, and handleAop matches the writes above the gate so a write route can never consult one. The seal is HMAC-SHA256(key = the stored passcode digest, msg = the keycard), which means no new server secret to persist and no session table: it survives a restart, it proves nothing about another office, and changing or clearing the passcode invalidates every browser's copy at once. passcodeOk also passes a write token straight through, so an owner cannot lock themselves out of the room they just locked.

Guessing is bounded by a per-office attempt limiter as well as a per-client one, and the first is the one that matters: the client key is a header behind a proxy and therefore spoofable, while the office key is in the path. Without it a short passcode would be worth nothing however good the KDF, so the limiter and the scrypt parameters are two halves of one control. Only wrong attempts count, and both limiters are checked before the KDF runs — an unmetered attempt route would be a way to spend the server's CPU as well as a way to guess.

The app shell is deliberately ungated. index.html is byte-identical for every office, so serving it reveals nothing and the passcode prompt is ordinary client UI reacting to 401 {"passcode": true} (src/ui/passcode-prompt.js). There is no login page and no new template anywhere, which is what keeps / and the demo office out of reach of the gate — the one failure mode this could have had, and the thing test/office-owner.test.js names a test after. ?peek degrades to {keycard, reserved, passcode, locked} rather than refusing, because reception uses it to ask whether an office in your history is still there and a 401 there would strike a live office out of the only list that records it exists.

Creating an office is the one thing on that surface that needs no credential at all, and it cannot be gated without breaking the product: reception's front door and a link shared before the room exists both depend on it. So it is bounded instead — a sliding-window rate limit per client and across the whole server, and a hard cap on how many offices may exist (lib/rate-limit.cjs, MAX_OFFICES in lib/office-store.cjs). The limits sit at every door that creates a room rather than only on the mint route, because a first GET on an invented keycard and an unauthenticated POST to one both create an office too, and a cap that guarded one of three doors would not be a cap. Every refusal names which limit was hit and when to come back — 429 for a rate, 503 for the cap, since a rate is not the problem there — and reception prints that sentence rather than a status code. The defaults, the reasoning behind each number and the ROVING_OFFICE_MAX_OFFICES / ROVING_OFFICE_MINT_* / ROVING_OFFICE_TRUST_PROXY overrides a deployment sets are documented where they are declared, at the top of server.cjs and lib/office-store.cjs.

Events have to land somewhere in particular, and there is one endpoint.json per machine holding one URL — so exactly one office receives local hooks. That office does not have to be on this machine: node bin/aop-connect.cjs <url> writes the same file pointing at a remote receiver, and AOP_URL/AOP_TOKEN override it for a single shell. Only a server started with --publish writes that file at all — npm run serve does, a bare node server.cjs does not, so the four servers running one per worktree cannot take the feed from the office you are watching. Within a publishing server, the office you open takes the endpoint if any of its scenes wants live agents, which means a glance at the demo office cannot quietly unplug your work; node server.cjs --publish 8080 --office K7F2-9QBX pins it instead. The chip beside the office name is lit when the room you are looking at is the one being fed.

Adapters read that URL rather than building one, so nothing under bin/ or hooks/ knows that keycards exist. You can drive the whole thing by hand:

EP=$(node -p "JSON.stringify(require(require('os').homedir()+'/.roving-office/endpoint.json'))")
URL=$(node -p "($EP).url"); TOKEN=$(node -p "($EP).token")
curl -s -X POST "$URL" -H "Authorization: Bearer $TOKEN" \
  -d '{"aop":"0.1","id":"1","type":"session.start","harness":{"name":"claude-code"},
       "session":{"id":"S1","label":"hand-rolled"},"payload":{"source":"startup"}}'

The unprefixed /aop/v0/* paths remain as an alias for whichever office currently holds the endpoint, so a recipe written before offices had addresses still works.

Because the layout lives entirely in layout.js, moving a desk automatically moves its chair, its occupant's seat position, and the walkable map around it. That is also what makes the furniture editor small: it drags a prop, writes the number back into the layout, and asks the room to re-derive itself.

It is what makes the layout algorithm possible at all, for the same reason: a whole room is one blob written into that singleton, so a seed can produce an office without a line of scene code knowing it was generated. src/plan/ writes positions; everything downstream derives itself from them exactly as it does after a drag.

The same file says which furniture exists, and how much of it there may be — one mailbox, any number of bookshelves, one agent per desk. Adding a piece writes an instance into the layout and the room reconciles itself against it, so the count of desks is data rather than a number repeated in four places.
